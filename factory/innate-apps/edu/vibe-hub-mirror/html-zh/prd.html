先写清谁、在什么场景、遇到什么问题，并标明哪些是事实、哪些是假设。

PRD 按“背景 → 目标 → 概念 → 原型 → 范围 → 验收”把判断逐层对齐，技术方案可以链接进来，但不替它做决定。

PRD 怎样让团队对同一件事达成共识

先写用户问题和目标：说明哪类用户在什么场景遇到什么阻碍，以及这次希望改变什么结果；功能名称本身不能代替问题。

明确范围与非目标：写清本次必须覆盖的用例、约束和暂不处理的内容，让设计与开发知道哪些选择仍可讨论。

确立衡量成效的验收标准：用可观察的验收条件或成功信号检查结果，并把假设、待确认问题和后续更新留在同一份协作文档中。

容易混淆的地方

PRD 不是路线图、技术设计或线框图：路线图安排一段时间内的方向与优先级，技术设计说明系统怎样实现，线框图呈现界面结构；PRD 聚焦当前需求的用户问题、目标、范围和成功标准，可以链接这些材料，但不能由它们互相替代。
