消息队列Message Queue

你可能会说

导出大报表要等很久，能不能先给我一个任务编号，让后台慢慢生成，并在页面上看到等待、处理中、完成或失败？

在发送方与处理方之间暂存待处理消息，让双方不必同时在线或同步等待的通信与解耦机制。·例如用户导出大报表时，接口先创建任务，把任务 ID 和生成要求写入消息队列，再立即返回“等待处理”。后台 Worker 按能力取出任务、生成文件，并把同一个任务 ID 更新为 completed 或 failed。入队成功只代表队列收到了消息，不代表文件已经生成；发生重试时，同一任务还可能被再次处理。

一次报表导出怎样经过消息队列

失败前：页面一直等后台做完：用户点击导出后，请求同时查询数据、生成文件并上传存储。只要其中一步很慢，页面就会长时间转圈甚至超时，而且用户拿不到一个可以继续查询的任务状态。

接入队列，并用任务编号反馈状态：接口创建 export_104，把参数和编号写入队列后返回页面；工作进程领取它时更新为处理中，成功则记录文件地址，失败则记录可读原因。页面始终用同一个编号显示排队中、处理中、已完成或失败。入队只表示已受理，不表示文件已经生成。

改善证据：四处记录能够对上：验收时核对接口响应、队列消息、工作进程日志和页面最终状态都包含 export_104。还要重试一次失败任务，确认不会因重复消费生成两份文件；只有一条“消息已入队”日志不能证明任务完成。

入队成功不等于处理成功

队列的顺序和投递次数取决于具体产品与配置。为了避免消息丢失，常见方案会在未确认时重新投递，因此同一任务可能执行不止一次；Worker 要能识别重复任务，系统也要记录失败、重试和最终状态。这里不展开具体中间件配置。
