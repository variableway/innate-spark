Server Logs

You might say

There's an error in production. Where can I see what happened on the server?

Record what the server did so problems can be traced·Server logs capture requests, errors, background jobs, and important state changes. Useful logs include time, severity, and a request or job identifier. Avoid recording passwords, tokens, and unnecessary personal data, and connect related events so one failure can be followed across services.

When to use it

  • Investigate failed requests
    A traceable log entry
    12:08:31 INFO req_8fa2POST /api/orders · 201 · 184ms
  • Monitor background jobs
    Users and developers see different levels of detail
    Page messageUnable to save right now. Please try again.Server logDB timeout · stack trace
  • Trace one request across several steps
    Use a request ID to connect one request
    req_8fa2 · request receivedreq_8fa2 · payment checkedreq_8fa2 · order created
  • Record important operational events
    Turn individual logs into monitoring
    Past 5 minutes8.2% error rateAlertOn-call staff notified

When NOT to use it

  • Log passwords, tokens, or full private payloads
    Logs must not record sensitive information.
    password=123456token=eyJhbGciOi••••cookie=session=••••
  • Write only a generic message with no context
    This log does not help with debugging
    16:42:09 ERROR Something went wrongMissing the request, action, object, and reason
  • Use console output as the only monitoring plan
    Log an error but still return success
    Database failure→console.error→200 OK
    Logs cannot replace retries, rollbacks, or failure responses.
  • Keep unlimited logs without retention and access rules
    Debug logs bury the real problem
