# 可行性分析：把本仓库做成个人工作站的文档与产品 Index

日期：2026-09-12  
范围：本仓库（`workspace`）先只放文档、记录、ideas、计划；实际开发放到不同子目录或独立仓库。  
依据：当前仓库几乎只有一份 [README.md](../../README.md)，领域清单已经有了，实现尚未开始。

## 1. 你在建的是什么

README 描述的不是一个产品，而是一个 **个人工作站的目录合同**：

| 域 | README 中的角色 | 适合放在本仓库的内容 | 不应放在本仓库的内容 |
| --- | --- | --- | --- |
| Infra | Self-host 基础设施 | 拓扑、选型、运行手册、待办 | 实际 compose / IaC / 密钥 |
| Product Center | 从头脑风暴到产品与工具 | 想法、分析、设计、规格、迭代记录、产品目录 | 应用源码、测试、CI |
| Marketing | 内容与社媒 | 选题、成稿、发布日历、工具笔记 | 投放后台、账号密码 |
| Feeds | 信息采集 | 源清单、摘要、阅读笔记 | 原始抓取库、大体量附件 |
| Teaching | 由浅到深的教程 | 大纲、讲义、练习说明 | 学员作业仓库、可运行课件工程（可另仓） |

编号在 README 里从 3 跳到 6，说明领域清单还在草稿态。这不影响可行性，但说明 **现在定的是「有哪些域」，不是最终目录名**。

一句话：本仓库是 **地图和档案馆**，不是工地。工地（实现）另开目录或仓库。

## 2. 为什么这个模型可行

对个人工作站，把「想」和「做」拆开，比 monorepo 全家桶更稳，原因有四条。

**生命周期不同。** 想法、分析、设计改得勤、颗粒度小、需要来回链；实现仓库要能独立 clone、独立 CI、独立开 Cursor Project。混在一起时，文档检索会被 `node_modules`、构建产物、历史分支噪声压过。

**Cursor 的上下文是按「当前打开的 Project」工作的。** 索引、`@Codebase`、Rules、Skills 都围着打开的根目录转。文档 hub 保持小而密，实现仓库保持小而专，Agent 一次只吃一类上下文，正确率更高。官方也建议百万文件级仓库按子树打开，而不是永远开根。

**你已经有「实现走子目录」的约束。** 这正好避免最常见的失败模式：index 仓库慢慢长成什么都往里扔的 dump。子目录可以是：

- 同机兄弟目录（推荐）：`~/innate/workspace` 与 `~/innate/products/foo`
- 本仓库里的 **指针目录**（只放 `links.md` / 规格，不放源码）
- 真正需要同仓版本锁定时再用 git submodule（成本高，默认不要）

**个人场景没有「多人同时改同一 monorepo」的协调税。** 拆仓的主要代价（跨仓 PR、统一版本）对一个人几乎不存在。链接用相对路径或本机绝对路径即可。

## 3. 和常见替代方案比

| 方案 | 做法 | 适合 | 不适合 |
| --- | --- | --- | --- |
| A. Hub + Spoke（推荐） | 本仓只放文档与索引；每个产品 / infra / 教程实现独立仓或独立目录；需要时用 `.code-workspace` 临时拼起来 | 你现在的目标 | 强要求「一个 git clone 带走全世界」 |
| B. 文档 monorepo，实现也塞子目录 | `products/foo/docs` 与 `products/foo/src` 同仓 | 极早期、一个人、产品不超过两三个 | 产品变多、Cursor 索引变脏、Rules 互相污染 |
| C. 纯笔记软件（Notion / Obsidian）+ 代码在 Cursor | 知识在外，代码在 IDE | 已经重度使用该工具 | 想让 Agent **同一套文件** 读规格再写代码；来回复制 |
| D. 一切都在一个 Cursor 大仓 | 文档、实现、抓取数据、教程工程全在 `workspace/` | 演示或周末玩具 | 作为长期个人工作站 |

A 的核心不是「必须多 git remote」，而是 **实现单元要能单独成为 Cursor Project**。git 可以后补；目录边界要先定。

Notion 可以作为对外或跨设备的镜像，但 **canonical 应留在本仓库的 Markdown**。这样 Cursor 能 `@` 文件、Rules 能引用模板、以后实现仓也能链回来。你这边已有 Notion skills，适合「发布 / 同步」，不适合当唯一真相源。

## 4. 主要风险（以及怎么防）

### 4.1 边界腐烂：文档仓长出实现

一旦某次「先在 `products/foo/` 里写个原型」没搬出去，三个月后这里会同时有规格、半成品代码、另一套 `AGENTS.md`。Cursor 会把它们一起索引。

**防法：** 根 `AGENTS.md` 写死「本仓库不承载产品实现」；每个产品目录只允许文档与指针；实现路径写在 `links.md`。Agent 若要写代码，必须先打开或挂上实现仓。

### 4.2 链接腐烂

实现在别的目录时，规格里的「见 `../foo/src`」很容易失效。

**防法：** 每个产品一个 `links.md`，只维护很少的稳定字段：本机路径、git remote、默认 Cursor Project 名。正文里只链 `links.md` 或文档，不链实现仓内部的深路径。深路径属于实现仓自己的 README。

### 4.3 Cursor 上下文膨胀

如果以后在本仓每个子域都放一份很长的 `AGENTS.md`，在部分 Cursor 版本里，嵌套 `AGENTS.md` 可能被当成 Always 规则被过多加载，撑爆上下文（社区在 monorepo 场景报过这个问题）。

**防法：** 根 `AGENTS.md` 短（一页内）；域级说明用 `.cursor/rules/*.mdc` + `globs`，按打开的文件按需挂载。不要在每个想法子目录复制一份 Agent 说明书。

### 4.4 多根工作区的规则串味

把 hub 和某个实现仓一起加进 multi-root workspace 时，**每个根上的根级 `AGENTS.md` 可能被全局加载**，而不是只作用于该根。这是已知行为，不是你的配置错误。

**防法：** hub 的根 `AGENTS.md` 只写「这是文档仓」这类不会伤害实现仓的句子；实现仓的硬约束放进 `.cursor/rules/*.mdc` 并带 `globs`。需要同时开两边时，心里默认「两边的根说明会见面」。

### 4.5 Feeds / 附件把索引拖死

信息采集若把网页快照、视频、原始导出丢进本仓，语义索引会变慢、检索会偏。

**防法：** 本仓只留源清单和笔记；大体量原始文件进旁路目录，并用 `.cursorindexingignore` 排除。需要时再 `@` 单篇笔记，而不是让 `@Codebase` 去扫附件。

### 4.6 双真相：README 大纲 vs 真实目录 vs 实现仓

三处各写一套「我们有哪些产品」，一周后必漂。

**防法：** 根 README 只做域地图；产品清单只在 `product-center/catalog.md`（或等价文件）维护一份；实现仓 README 链回 catalog 条目。Agent 规则写明：增删产品先改 catalog。

## 5. 判定标准：怎样算这套结构在工作

三个月后若下面大多为真，就继续；若多为假，再考虑把某个产品的文档挪进实现仓、本仓只留一行索引。

1. 打开本仓库时，Agent 能根据 catalog / 域 README 找到某个 idea 或规格，而不是靠你粘贴路径。
2. 打开实现仓时，Agent **默认看不到** 本仓里无关域的营销稿、教程、feeds。
3. 任意产品从 idea 到「开始写代码」有一次明确晋升（目录挪动或状态字段变化），而不是同一篇草稿被改到第 40 版还叫 idea。
4. 本仓库没有出现 `package.json` / `go.mod` / 应用源码（教学示例仓库除外，且应是独立 spoke）。
5. 你能用一句话回答「这个产品的实现在哪」——答案在 `links.md`，不在聊天记录里。

## 6. 建议决策（可直接当 ADR 用）

1. **采用 Hub + Spoke。** 本仓库 = index + 知识；实现 = 独立目录 / 独立 Cursor Project。
2. **本阶段不建 git submodule，不把实现 clone 进本仓。** 先把文档信息架构跑通。
3. **README 的域保留，目录名去数字前缀。** `infra` / `product-center` / `marketing` / `feeds` / `teaching`，避免以后插入 4、5 时全盘改名。
4. **`docs/idea` 只做跨域或尚未分域的分析。** 已属于某产品的想法，放到该产品的 `idea/`，避免第二套垃圾堆。
5. **先写规则和目录合同，再批量搬家。** 现在几乎是空仓，成本最低的窗口就是此刻。
